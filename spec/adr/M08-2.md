# ADR M08-2 — Media token and self-signed playback

Status: security constraints accepted in M03. The AVPlayer prototype itself belongs to M08.

## Context

Jellyfin API calls send `Authorization: MediaBrowser ...`. AVPlayer does not use the app `URLSession` delegate, so it will not attach that header and will not enforce S4.6 redirects or S4.4 certificate pins. Jellyfin documents `ApiKey` as a last resort because it leaks into reverse-proxy logs. Jellyfin 12 removed `api_key`.

## Decision

1. Prefer the Authorization header for media. The order is `AVAssetResourceLoaderDelegate` (documented), then the undocumented `AVURLAssetHTTPHeaderFieldsKey` (`ResolvedMediaURL.httpHeaderFieldsKey`). M08 proves which of those works on tvOS 26/27.
2. `ApiKey` is allowed only as a fallback, and only on media URLs built by `MediaRequestBuilder` in `MediaURL.swift`. Header mode and query mode are mutually exclusive. Images and API calls never add `ApiKey`.
3. AVPlayer receives only a URL that Glassfin has already resolved with its own `URLSession` under S4.6 (`MediaURLSecurity`). Direct play probes with `HEAD /Videos/{id}/stream`. HLS probes with GET of the master playlist. A cross-origin result or an HTTPS→HTTP result is not passed to AVPlayer.
4. `ApiKey` on HLS segment URLs that the server itself generates is an accepted risk, as long as redaction and this redirect rule stay in place.
5. Self-signed media stays a known limitation until the resource-loader path exists. API calls can pin; AVPlayer cannot, because it bypasses the app delegate.

## Consequences

- Logging a media URL goes through `SensitiveRedactor` before it reaches `os_log`, stderr, or a description.
- A redirect loop or a sixth same-origin hop fails closed.
- M08 still has to measure the resource loader against direct play, server HLS, and a loopback remux.
